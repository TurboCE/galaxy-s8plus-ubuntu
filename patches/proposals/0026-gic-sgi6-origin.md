# CPU-startup SGI6 origin: unresolved, no handler-change patch

No applicable 0026 patch is supplied. This note is outside `patches/*.patch`.
No BOOT write, reboot, CPU hotplug, trace enable or runtime setting was performed.
Silently accepting every SGI6 is not justified by the available evidence.

## Proven source/configuration path

Pinned kernel: `54feaea9870dd0e90ceced5623e0544d965b400b`, deployed build #22,
GNU build-id `a20011287705b191ee878520a4a3eff5c82c9655` from
`artifacts/kernel-pcie-clock-bounds/vmlinux` (previous live identity verified).

- `arch/arm64/kernel/smp.c`: enum IPI_WAKEUP is 6. Both the explicit wakeup
  sender (`arch_send_wakeup_ipi_mask`) and its handler are guarded by
  CONFIG_ARM64_ACPI_PARKING_PROTOCOL. The selected config has ACPI disabled.
- The selected Exynos8895 DT assigns `enable-method = "psci"` to all CPUs,
  uses the SMC conduit and PSCI v0.1 CPU_ON ID 0xc4000003. The #22 log confirms
  this PSCI setup. `arch/arm64/kernel/psci.c:cpu_psci_cpu_boot()` invokes `psci_ops.cpu_on`
  with `secondary_entry`; it contains no Linux SGI6 send.
- The CPU GIC DT is Cortex-A15/A9-compatible GICv2 at 0x10201000/0x10202000.
  `drivers/irqchip/irq-gic.c:gic_handle_irq()` obtains the raw IAR, extracts
  interrupt ID 6, performs the existing EOI/deactivation, then calls
  `handle_IPI(irqnr, regs)`. Its source-CPU information is not passed along.
  Thus the error does not mean the hardware interrupt was left unacknowledged.
- `gic_raise_softirq()` is the normal Linux send path. The arm64 call sites
  request reschedule/call/single-call/stop/timer/irq-work IPIs; no compiled
  explicit IPI6 sender was found. Generic GIC SGI forwarding/migration exists
  under CONFIG_BL_SWITCHER, which is not enabled for this arm64 target.
- ABOX has a separate GIC at 0x13ef1000; its software interrupts must not be
  equated with CPU GIC SGIs solely because both use the SOFTINT register offset.
- `gic_secondary_init()` invokes `gic_cpu_init()` on CPU_STARTING.
  `irq-gic-common.c:gic_cpu_config()` clears active state, disables PPIs,
  enables SGIs and initializes priorities. It does not clear pending SGIs.
  A firmware/bootloader-pending wake SGI is therefore possible, not proven.

## Minimal next observation, only in a separately reviewed diagnostic build

Preserve the existing unknown-IPI error and every existing EOI/deactivate/write.
Do not enable ACPI parking on this DT to make a warning disappear, clear pending
SGIs wholesale, renumber IPIs, or replace the default handler with a no-op.

A narrow diagnostic candidate could record:

1. The banked GICv2 SGI6 pending-source byte before enabling each secondary's
   CPU interface. SGI6 occupies bits 23:16 of the pending register covering
   SGI4..7 (`GIC_DIST_SGI_PENDING_SET + 4`). A non-destructive register read is
   enough; no write-to-clear or extra INTACK read should be introduced.
2. For SGI6 only, the existing raw IAR value before it is reduced to irqnr,
   destination CPU, startup/online phase and timestamp. The GICv2 source CPU
   interface field can be decoded only with the applicable GIC contract; it
   identifies a source interface, not the software/security-world sender.
3. Linux SGI6 send attribution in `gic_raise_softirq` (and any enabled direct
   send path), retaining the ordinary IPI tracepoint. A matching kernel send
   would establish a Linux origin; absence alone does not prove which firmware
   component generated it. Diagnostics must cover early startup, before trace
   buffers are assumed available.

Correlate those records with the unchanged PSCI CPU_ON path and a matching stock
kernel/firmware contract. If the SGI is a stale firmware wake notification, a
platform-specific handler or properly owned handoff fix must be based on that
contract. If it arrives after bring-up or is generated by Linux, fix the actual
sender/protocol mismatch instead. Future CPU hotplug/suspend validation needs
separate authorization and recoverability planning; none was attempted here.
